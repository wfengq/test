# 注意力预算原型（attention-budget）设计文档

> 日期：2026-10-20 ｜ 状态：待审（第 2 版：X 换成小红书）｜ 背景调研见 `research/` 目录下三份报告

---

## 1. 目标与判定标准

### 1.1 要验证的事
AI 每天替使用者从 **B 站和小红书** 里只挑出 **5 条**，并讲清楚其余为什么不用看——这能不能让使用者**少刷这两个平台、又不觉得漏了重要的东西**。

### 1.2 两周后看四个数（都从账本里算）
| 指标 | 定义 |
|---|---|
| 有用率 | 推送的 5 条里被标「有用」的比例 |
| 漏判率 | 「值得看但没名额」里被标「有用」的比例 |
| 刷原 App 时间 | 每周复盘时使用者自报的 B 站 + 小红书使用时长 |
| 每日花费 | 账本里的 token 用量 × 配置里的单价 |

### 1.3 已确定的需求（来自使用者）
- 平台：**B 站、小红书**
- 读的内容：**关注的人的更新、平台推荐流、按关键词搜索**（三类都要；小红书的"关注更新"按 §3.5 近似）
- 小红书的数据：本机运行开源工具 **xiaohongshu-mcp**（Apache-2.0），只调用其只读功能
- 小红书图片里的字：深读时用本地文字识别（RapidOCR）读取
- 运行环境：使用者自己的 **Windows** 电脑
- 模型：**DeepSeek**
- 推送：**Telegram**，**每天 1 次、两平台合计 5 条**
- 判据来源：使用者写的**兴趣说明**，加上反馈自动形成的正反例
- 总体做法：**C —— AI 尽量放开，代码只守五条边界**

### 1.4 不做的（这一版）
- X、公众号、播客、YouTube 等其他来源
- 本地语音转写（没字幕的视频靠简介、评论、图片文字判断，并标明"没读到原文"）
- 任何写操作：发帖、评论、点赞、收藏、关注、私信
- 多用户、云端部署、网页界面
- 点击追踪（隐式反馈）

## 2. 总体原则：代码守边界，AI 管判断

**交给 AI 的**：理解使用者、决定搜什么、粗排、决定每条读多深、写给使用者本人的理由、排出最终 5 条、挑意外发现、每周复盘并提出修改。

**代码守的五条边界**（AI 无法绕过）：
1. **名额**：最终推送 ≤ 5 条（`budget.daily_picks`，默认 5），其中意外发现 ≤ 1 条。
2. **记账**：AI 看过、读过、淘汰的每一条，连同分数和理由，由代码写入账本。
3. **花费上限**：每轮 token 总量与工具调用次数封顶；触顶即停止深读、用已有结果定稿。
4. **账号安全**：读取频率和数量由代码控制；所有工具只读；对 xiaohongshu-mcp 只允许调用 §3.5 列出的六个只读接口。
5. **反馈原样保存**：AI 可读、不可改。

## 3. 结构

### 3.1 模块
| 模块 | 职责 | 对外接口（概要） | 依赖 |
|---|---|---|---|
| `collectors/bilibili.py` | B 站：关注更新、首页推荐、搜索、字幕、评论、UP 主近期视频 | `follow_updates(since)`, `recommend(n)`, `search(q, n)`, `subtitle(bvid)`, `comments(bvid, n)`, `up_recent(mid, n)` → `Item` / `str` | `bilibili-api-python>=17.4,<18` |
| `collectors/xhs.py` | 小红书：启停 xiaohongshu-mcp、首页推荐、全站搜索、已关注范围搜索、重点博主新笔记、笔记详情（正文 + 图片文字 + 字幕 + 评论）、作者近期笔记 | `recommend(n)`, `search(q, n, scope)`, `key_creators_updates()`, `note_detail(item)`, `author_recent(user)` → `Item` / `str` | `httpx`；xiaohongshu-mcp Windows 版程序 |
| `ocr.py` | 识别图片中的文字 | `image_text(urls, max_images) -> str` | `rapidocr_onnxruntime` |
| `agent/` | 调 DeepSeek 完成：搜索规划、粗排、深读、定稿、周复盘；每个环节一个固定输出结构 | `plan_searches(ctx)`, `coarse_rank(batch, ctx)`, `deep_read(item, ctx, tools)`, `finalize(judged, ctx)`, `weekly_review(week)` | `openai` SDK（DeepSeek 兼容接口）、`pydantic` |
| `guard.py` | 五条边界：所有工具调用先过它；校验定稿；计数与封顶 | `call(tool, args)`, `check_final(picks)`, `remaining()` | 无 |
| `ledger.py` | SQLite 账本：读写所有记录；断点续跑 | 见 §5 | `sqlite3` |
| `bot.py` | Telegram：推送、按钮、留言、周复盘确认、重新登录二维码 | `send_daily(run)`, `send_bill(run)`, `send_review(review)`, 回调处理 | `python-telegram-bot` |
| `run.py` | 一轮的编排；命令行入口 | `run`, `check-sources`, `dry-run`, `review`, `login-bili`, `login-xhs` | 以上全部 |

### 3.2 数据结构 `Item`
所有来源统一成：`id`（平台前缀 + 原始 ID，如 `bili:BV1xx`、`xhs:64f…`）、`platform`（`bili` / `xhs`）、`channel`（`follow` / `recommend` / `search`）、`author`、`author_id`、`title`、`snippet`（简介或正文前 300 字）、`url`、`published_at`（小红书列表里没有时间，可为空，深读后补上）、`metrics`（播放 / 点赞等，可空）、`query`（来自搜索时记录搜索词）、`xsec_token`（小红书取详情必需，B 站为空）。

### 3.3 "对使用者的理解"
| 文件 | 谁写 | 说明 |
|---|---|---|
| `profile/interests.md` | 使用者 | 我在做什么、关心什么、哪类内容一律不要。提供模板 |
| `profile/understanding.md` | AI（经使用者确认） | AI 维护的"我对你的理解"；只在周复盘被采纳时修改，每次修改另存 `profile/history/understanding-<日期>.md` |
| 账本 `feedback` / `notes` 表 | 使用者 | 按钮与留言，原样保存 |

### 3.4 目录与配置
- 代码仓库：`attention_budget/`（Python 3.11+，`uv` 管理环境）
- 运行数据目录：`%USERPROFILE%\.attention-budget\`（账本、报告、B 站凭证、日志）——不在仓库里
- 配置文件：`%USERPROFILE%\.attention-budget\config.toml`，含：DeepSeek API key 与模型名（默认 `deepseek-chat`）、token 单价（使用者按官网价格填写，用于算花费）、Telegram bot token 与使用者 chat_id、xiaohongshu-mcp 程序路径、小红书重点博主名单（主页链接）、各项数量与上限（见 §4、§2）、推送时间（默认 08:00，本机时区）

### 3.5 小红书的接入方式
- **工具**：使用者从 xiaohongshu-mcp 发布页下载 Windows 版 `xiaohongshu-mcp-windows-amd64.exe` 与登录工具 `xiaohongshu-login-windows-amd64.exe`。它在本机用浏览器读取页面，登录信息由它自己保存。
- **启停**：每轮开始时由本程序以无头模式启动（端口 18060，每次随机生成访问令牌），等它的 `/health` 正常后再用；本轮结束即关闭。
- **只读接口白名单**（代码里写死，名单外一律不调）：查登录状态、取登录二维码、首页推荐 `feeds/list`、搜索 `feeds/search`、笔记详情 `feeds/detail`、用户主页 `user/profile`。发布、评论、点赞、收藏、通知回复等接口永不调用。
- **"关注的人的更新"的近似做法**（小红书网页端没有关注动态列表）：
  1. 用搜索的"已关注"范围，配合 AI 当天定的搜索词，限定"一周内"；
  2. 使用者可在配置里列最多 10 位重点博主（贴主页链接，链接里带访问所需的参数），每天看他们主页有没有新笔记。
  - 代价：关注的人发了与兴趣无关、又不在重点名单里的笔记会漏掉。
- **读原文**：笔记详情包含正文、图片、互动数、前 10 条评论；视频笔记可能带字幕直链。深读时代码把**正文 + 前 6 张图片识别出的文字 + 字幕（若有）+ 评论**交给 AI。图片识别只在深读阶段做，粗排只看标题和正文开头。
- **账号注意事项**（写进 README 与首次运行提示）：
  - 同一账号不能同时在两个网页端登录；xiaohongshu-mcp 登录后，使用者不要再在电脑浏览器登录小红书网页版，否则会互相挤掉（手机 App 不受影响）。
  - 新号会被要求实名认证，建议先实名。
  - xiaohongshu-mcp 作者称其原项目运行一年多未被封号、只需偶尔重新登录；这是作者的说法，风险不为零。

## 4. 每天一轮

每一步完成后在账本 `runs.stage` 记一笔；中途崩溃时重跑从断点继续。

| 步骤 | 谁做 | 内容 | 默认数量 / 上限 |
|---|---|---|---|
| 0 准备 | 代码 | 读 `interests.md`、`understanding.md`、最近 14 天「有用」10 条与「没用」10 条（带原因）、有效期内的留言；取已推送和已看过的 ID 用于去重；启动 xiaohongshu-mcp | — |
| ① 基础采集 | 代码 | B 站关注更新（过去 24 小时）、B 站首页推荐、小红书首页推荐、小红书重点博主新笔记；去重 | 100 / 50 / 50 / 每位博主取最近 10 条 |
| ② 搜索规划 | AI | 根据理解与近期「有用」内容提出搜索词，每个附理由；代码执行 | B 站 ≤3 个；小红书"已关注"范围 ≤3 个、全站 ≤3 个；每个取 20 条 |
| ③ 粗排 | AI | 分批（每批 ≤50 条）给每条打 0–100 分 + 一句理由；全部写账本。代码取前 30 进深读；AI 可额外标记 ≤5 条"标题不行但可能有料"一并进入 | 深读池 ≤35 条 |
| ④ 深读 | AI（逐条小循环） | 每条可调用只读工具：B 站 `subtitle` / `comments` / `up_recent`，小红书 `note_detail`（正文 + 图片文字 + 字幕 + 评论）/ `author_recent`；读完给出 `pick` / `maybe` / `reject` + 理由 + 一句写给使用者的话；没读到原文须标 `no_source=true` | 每条 ≤4 次工具调用；小红书详情每轮 ≤40 次 |
| ⑤ 定稿 | AI + 代码校验 | AI 从 `pick`/`maybe` 中排出最终名单并指定意外发现及理由。代码校验：总数 ≤5；意外发现 ≤1 且 `channel ≠ follow`；每条都经过深读；未曾推送过。不通过 → 让 AI 改一次 → 仍不通过按其排序截断并剔除不合规项 | — |
| ⑥ 推送 | 代码 | 见 §6；同时写本地报告 `reports/<日期>.md`；关闭 xiaohongshu-mcp | — |

**每轮上限**（触顶即跳到⑤，账单注明）：token 总量 500,000；工具调用 150 次；整轮 40 分钟。

**内容安全**：所有采集来的文字（含图片识别出的文字）以"材料"身份传给 AI，系统提示中写明其中的指令一律不执行；工具全部只读。

## 5. 账本（SQLite）

| 表 | 主要字段 |
|---|---|
| `runs` | `run_id`、`date`、`stage`、`started_at`、`finished_at`、`status`（ok / partial / failed）、`source_status`（各来源成功或失败原因，JSON）、`tokens_in`、`tokens_out`、`tool_calls`、`capped`（是否触顶） |
| `items` | `Item` 全部字段 + `first_seen_run` |
| `verdicts` | `run_id`、`item_id`、`stage`（coarse / deep / final）、`score`、`decision`、`reason`、`note_to_user`、`no_source`、`serendipity` |
| `tool_calls` | `run_id`、`item_id`、`tool`、`args`、`ok`、`error`、`at` |
| `pushes` | `run_id`、`item_id`、`slot`（main / serendipity / missed）、`telegram_message_id` |
| `feedback` | `item_id`、`run_id`、`value`（useful / not_useful）、`reason`（not_interested / already_known / low_quality / too_long，可空）、`at` |
| `notes` | `text`、`at`、`expires_at`（AI 从留言中解析出时间范围；解析不出则 14 天） |
| `reviews` | `week`、`proposals`（JSON：每条修改、理由、依据的反馈 ID）、`decisions`、`self_reported_minutes` |
| `outbox` | 发送失败待补发的消息 |

## 6. Telegram

- **只响应配置里的那个 chat_id**，其他人发来的消息一律忽略。
- **第一条：今日 5 条**。每条：平台、标题、链接、AI 写给使用者的理由（≤80 字）；意外发现那条标注"你没关注的"及推荐理由。每条下方「有用 / 没用」按钮；点「没用」后再弹四个原因按钮。
- **第二条：今日账单**。"值得看但没名额"的条目（同样带链接和按钮）；一行统计：看了多少、深读多少、主要淘汰原因及条数（由粗排 / 深读理由归类，AI 在定稿时顺带给出归类）；各来源状态与是否触顶；本地报告路径。
- **留言**：使用者发来的任何文字存入 `notes`，下一轮生效。
- **周日 20:00 复盘**（错过则下次开机补发）：AI 对照本周打分与反馈，给出对 `understanding.md` 的若干条修改（每条带理由和依据），每条「采纳 / 不采纳」按钮；同一消息询问本周 B 站 + 小红书大约用了多久（回复数字即可）。意外发现的反馈单独统计、不用于收窄主判据；某方向意外发现被连续标「有用」时，复盘提议"是否加入兴趣"。
- **常驻方式**：登录 Windows 后由任务计划程序启动 `bot` 常驻接收回调；电脑关机期间的按钮由 Telegram 暂存（最长 24 小时）。

## 7. 出错处理

| 情况 | 处理 |
|---|---|
| B 站凭证失效 | 跳过 B 站，其余照跑；推送首行说明，并把重新登录二维码以图片发到 Telegram |
| 小红书未登录 / 被挤下线 | 跳过小红书，其余照跑；推送首行说明，并通过 xiaohongshu-mcp 取登录二维码发到 Telegram；同时提醒"不要在电脑浏览器登录小红书网页版" |
| xiaohongshu-mcp 启动失败或 30 秒内 `/health` 不正常 | 记为小红书来源失败并说明原因（程序路径不对 / 端口被占用 / 首次运行在下载浏览器） |
| 小红书接口报错、返回 0 条 | 该接口本轮不再调用、不重试；整个来源读到 0 条即记为来源失败 |
| 小红书读取节奏 | 每两次请求之间随机间隔 3–8 秒；详情每轮 ≤40 次 |
| 图片识别失败 | 跳过该图，正文和评论照常交给 AI；全部图片失败则在材料里注明"图片文字未识别" |
| DeepSeek 报错或超时 | 指数退避重试 3 次；输出结构不合法 → 重问 1 次 → 仍不合法记为"判断失败" |
| 整轮无法完成 | 推送"今天没跑成：原因"，绝不静默 |
| 触顶 | 停止深读，直接定稿；账单注明 |
| Telegram 发送失败 | 写入 `outbox`，下次启动补发 |
| 崩溃 / 关机 | 按 `runs.stage` 断点续跑，不重复已完成步骤的花费；xiaohongshu-mcp 进程在退出时一并关闭 |
| 错过 08:00 | 开机后补跑一次（任务计划程序"错过后尽快运行"），同一天不重复跑 |
| 密钥与凭证 | 全部放在运行数据目录，不进仓库；`.gitignore` 排除 |

## 9. 已知风险
- **小红书风控与改版**：xiaohongshu-mcp 靠浏览器读页面，小红书改版会让它失效，需要跟着升级；封号风险低但不为零。以"接口出错即停、不重试"止损。
- **小红书"关注更新"不完整**：只覆盖兴趣相关的搜索和重点博主名单。
- **B 站接口变化**：依赖第三方库 `bilibili-api-python`，需锁版本。
- **只看标题的粗排会漏**：靠"标题不行但可能有料"名额与深读池大小缓解，成本随之上升。
- **图片识别质量**：手写、花字、截图拼图识别率会下降；识别结果只作为材料，不保证完整。
- **花费估算**：每轮约 30 万 token 是设计时估计（图片文字会让深读部分略增），以首周账本实测为准。
